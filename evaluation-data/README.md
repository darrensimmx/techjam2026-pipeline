# External evaluation data — read this before using anything in here

**Purpose:** external, real-world language used to *test* whether our components
hold up outside the shipped simulator. It exists so a robustness claim rests on
data nobody on this team wrote.

**The discipline:** treat everything under this directory as **test-time only**.
Do not read it, sample from it, or tune against it while writing the component
it is meant to test. That applies to a human developer and to an AI assistant
equally.

---

## This is a policy, not a mechanism — read this part carefully

Nothing here is enforced by code. These are plain files in a git repo. Any
developer, and any AI assistant with filesystem access, can open them; no script
checks who read what, and no script can. If you point an agent at this repo and
ask it to build the reply parser, **nothing stops it reading the test data
unless you tell it not to.**

This directory does not change that. It records intent and provenance, and it
gives the two a single place to live. `features/reply-parsing/paraphrase-robustness-prompt.md`
in the planning repo already states the principle this follows:

> A README in the folder saying "don't look" is a marker of intent, not a
> control — the control is that the holdout is generated separately and never
> read during development.

So the real guard is always **provenance**, never access. What that guard is
worth depends on who authored the data, and it is not the same for everything
filed here:

| data | authored by | what reading it during development would cost |
|---|---|---|
| `esci/` (below) | real Amazon customers; labels by Amazon annotators | you could overfit a retrieval config to these 600 queries. The *distribution* still is not ours, so the data cannot become circular. Bounded damage. |
| a self-authored paraphrase corpus (not built yet) | us | reading it **is** the circularity. The measurement stops meaning anything. Unbounded damage. |

Those are different risks and deserve different care. The second one is the case
where a holdout must be generated by a separate prompt and never opened — see
the paraphrase prompt for the full protocol, and note that this project has
already been burned once: a cue-based fallback scored 100% on 15 paraphrases
written by the same person who wrote the cue lists.

If you want an actual control rather than a policy, the options are real but
none of them live in a README: keep the holdout out of the working tree
entirely (separate private repo, or generated at scoring time from a seed held
elsewhere), or have the scoring script be the only thing that ever decrypts it.
Until one of those exists, this is an honour system, and it should be described
as one.

---

## What is filed here

### `esci/` — real human shopping queries (retrieval robustness)

Not paraphrases. Real Amazon customer search queries, used to answer one
question the public set cannot: **is "BM25 beats dense" a fact about retrieval,
or a fact about a simulator that copy-pastes?**

`bakeoff/overlap.py` measures **94.5%** of the simulator's disclosed constraint
strings as verbatim substrings of the target product's own listing — because
`evaluator/local_evaluator.py:52-71` builds them by copying out of it. On a
corpus like that, exact term matching is close to the ideal algorithm by
construction. That makes a BM25 win on the public set consistent with two very
different worlds, and the public set alone cannot separate them.

Writing our own paraphrases would not separate them either: we would invent the
distribution that decides the answer, then report what we invented. So the
queries come from outside:

> Reddy, Màrquez, Valero, Rao, Zhang, Sanz, Nag, Nagaraj, Karim, Rowe, Nio, Zhu.
> **"Shopping Queries Dataset: A Large-Scale ESCI Benchmark for Improving
> Product Search."** arXiv:2206.06588, 2022.
> <https://github.com/amazon-science/esci-data> — Apache-2.0.
> Mirror used: HuggingFace `tasksource/esci`.

130k real Amazon queries, 2.6M human Exact/Substitute/Complement/Irrelevant
relevance judgements over real ASINs.

**A route that was tried and abandoned — recorded so nobody spends the download
again.** The first plan was to run ESCI queries against *our* catalog, by
intersecting ESCI's `product_id` with our `parent_asin`. Measured: **71 shared
ASINs** out of 599,151 ESCI products × 50,000 of ours, and **zero** surviving
the `locale == us AND esci_label == Exact` filter. The two are near-disjoint
samples of Amazon. Dead end.

**What is built instead:** a standalone 20,000-product corpus written in *our
catalog's exact JSONL schema*, so `starter/retrieval.py`'s `Bm25Index` indexes
it unmodified — same FTS5 tokenizer, same column weights — and the same encoders
run over it. 600 human queries, 5,036 judged-Exact targets, seed 20260829.

#### `esci/esci_public_set.jsonl` — committed, drop-in for the organizer's tooling

600 samples in `data/public_set.jsonl`'s schema, so `load_jsonl`,
`catalog_index` and `evaluate()` all take it unchanged. One deliberate
departure, and it is load-bearing: each sample also carries `intent_card` and
`behavior`, which the organizer's public set does **not**.

That is not decoration. `local_evaluator.py:204-206` returns a supplied
`intent_card` verbatim and otherwise falls through to building the customer's
hidden preferences out of *the target product's own listing* (`:52-71`). Emit
ESCI in the public set's literal shape and the evaluator would discard every
human query and regenerate a copy-pasted one — deleting the entire reason this
dataset exists. The keys are there to stop that. Round-trip verified: the human
query reaches the opener in 600/600 samples.

Fields with no ESCI counterpart (`category_bucket`, `difficulty_bucket`,
`user_profile`) are `"unknown"` / empty rather than invented, and the profile's
`summary` says so in words so it cannot be quoted as real.

```sh
.venv/Scripts/python bakeoff/esci.py                  # -> bakeoff/cache/esci_catalog.jsonl
.venv/Scripts/python bakeoff/esci_public_schema.py    # -> esci/esci_public_set.jsonl
.venv/Scripts/python bakeoff/part5_realqueries.py     # retrieval-only measurement

python -m evaluator.local_evaluator \
  --catalog bakeoff/cache/esci_catalog.jsonl \
  --dataset evaluation-data/esci/esci_public_set.jsonl --output results_esci.json
```

The corpus itself (~28 MB) is generated, not committed, and fully reproducible
from the seed.

#### First result, and how to read it

The shipped agent, unchanged, scored through the real evaluator:

| | public set | ESCI real queries |
|---|---|---|
| TechnicalScore | 0.692586 | **0.409436** |
| HitRate@10 | 0.800 | **0.4867** |
| MRR | 0.5256 | **0.2292** |

**These two columns are not comparable as scores, and quoting the gap as
"−0.28" would be wrong.** Four differences, all of which cut the same way:
the corpus is 20,000 documents rather than 50,000; each ESCI session is a single
human query with no multi-turn accumulation, so the ledger — this project's
largest measured lever — never fills; ESCI queries average 8 judged-Exact
products but only one is recorded as `ground_truth`, so retrieving a *different*
correct product scores as a miss; and the opener frame adds a constant
`"clothing item"` category string ESCI has no value for.

So **0.409436 is a lower bound**, not a like-for-like score. What it is good for
is the direction: the public set's 0.80 hit rate is measured on queries that are
94.5% verbatim copies of the target listing, and on human language against the
same retrieval code the number is far lower. That is the bracket the leak
argument has always needed and never had.

Corpus size differs from our real 50,000-product catalog (CPU budget: every
document is encoded twice). Recall@k depends on corpus size, so **these numbers
are not comparable to the public-set recalls in Part 2** — only the
BM25-vs-dense ordering *within* this benchmark is.

### `paraphrase/` — not built yet

Reserved. When `features/reply-parsing/paraphrase-robustness-prompt.md` is
executed, its `dev/` and `holdout/` corpora land here, and the provenance record
it requires — *which prompt generated which split, and who saw what* — goes in
this file. That corpus is the self-authored case in the table above, so its
holdout needs a stronger guard than this directory provides today. Decide what
that guard is **before** generating it, not after.
